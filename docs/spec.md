# お題当てゲーム GM ボット 仕様書

セットアップ・環境変数・遊び方の手順は [README](../README.md) を参照。ここには、コードからは読み取りにくい目的・ルール・設計判断とその理由だけを残す。

## 目的と範囲

Discord で「お題当てゲーム」の GM（はい／いいえで答える役）をボットが担う。出題者がお題を登録し、参加者の質問に TypeSafe AI の Jev が「はい／いいえ」と割合で答え、言い当てたら「正解です」で 1 ゲーム終了。

Web 版: Discord の外のサイトで、ボタンを押している間に話した言葉を質問として送れる。ゲームの中核は Discord 版と共通だが、ゲームは別々に進む（Discord のチャンネルと Web のルームはつながらない）。

対象外: インサイダーゲームの役職・投票・タイマー、ボイスチャンネルの聞き取り、ゲーム状態の永続化（再起動で進行中ゲームは消える）、Web 版のログイン・ルームの保存・サーバー側での文字起こし・サイト内の通話。

## ゲームのルール

- 1 チャンネルにつき同時に 1 ゲーム。お題は出題者本人にだけ表示する（登録応答はエフェメラル）。
- 進行中のチャンネルでは、出題者以外のプレイヤーの発言のうち、末尾の空白を除いて「？」か「?」で終わるものだけを質問として扱う。お題の言い当ても同じ。それ以外の発言、ボットの発言、スレッド作成などのシステムメッセージは無視する。ゲーム中のチャンネルで雑談できるようにするため。
- ゲーム開始の通知で「質問は最後に「？」をつけてね」と案内する。「？」のない発言には返事をしない（雑談のたびにボットが反応しないため）。
- 質問数 = 判定に成功した質問の数（正解の質問を含む）。判定失敗は数えない。
- `/odai giveup` は誰でも実行できる。

## 判定

1. **完全一致の即決**（Jev を呼ばない）: 表記ゆれを正規化したうえで、質問がお題そのもの、またはお題＋問いかけ表現（「ですか」「かな」など）のときだけ正解とする。
   - 正規化は NFKC・小文字化・カタカナ→ひらがな・空白除去のみ。長音「ー」や記号は残す（「ビール」と「ビル」を区別するため）。漢字⇔かなの違いは Jev に任せる。
   - 1 文字の語尾（「か」「ね」）は取り除かない（お題「すい」に「すいか？」が一致するのを防ぐ）。部分一致も使わない。
2. **Jev**: `is_yes`（答えが「はい」か）と `is_correct`（お題を言い当てているか）の 2 つを 1 リクエストで問い合わせる。`is_correct` がしきい値（既定 0.8）以上なら正解。
   - 否定・比較・複数候補・お題を含む別のもの（「青りんご」）は正解にしない。
   - 指示文は `is_yes` が英語、`is_correct` が日本語。jev-latest での検証（各 15 ケース）で英語・日本語とも全問正答だったが、`is_yes` は英語のほうが否定・比較の質問で確率が低く出た。`is_correct` は日本語のほうが正解ケースの最小値（0.86）としきい値との差が大きかった。再検証は `scripts/jev_probe.py`。
3. 「はい／いいえ」のラベルは**四捨五入後の割合が 50% 以上なら「はい」**。生の確率で決めると `0.496` が「❌ いいえ　はい 50%」のように表示と矛盾するため。

### 失敗時

- タイムアウト（既定 10 秒）や例外のときは「判定できませんでした」と返し、質問数に数えない。
- 接続の確立は 2 秒、応答の無通信は 4 秒で打ち切り、全体 10 秒以内で最大 6 回再試行する。実機で接続確立が 10 秒止まる事象や、応答が 8.9 秒止まったあと 520 が返る事象があり、打ち切りが全体の上限と同じ長さだと再試行の余地がなかったため。
- 使っていない接続は 90 秒保持する。質問の間隔は 15〜60 秒あり、httpx 既定の 5 秒では毎回接続し直しになって、接続確立が止まる事象に当たりやすいため（api.typesafe.ai は 60 秒空けても接続を保っていた）。
- 判定失敗のログには経過時間と、応答にあれば `retry-after`・`cf-ray` を添える。520 が再試行されなかったのは `Retry-After` が残り時間を超えていたためと推定しており、その確認に使う。

## 設計上の判断

- **Discord 非依存の中核**: 質問の入口は `GameService.handle_question` の 1 か所で、戻り値は「本人向け」と「チャンネル向け」の本文だけを持つ。将来の音声入力をゲーム部分を変えずに足すため。
- **チャンネル単位の直列化**: 同じチャンネルの操作は 1 つのロックで順番に処理し、Jev の判定と状態更新が終わるまでロックを持つ。正解が同時に 2 件来ても正解通知は 1 回だけになり、giveup は実行中の判定の完了を待つ。
- **古い質問の排除**: ロック待ちの前に進行中ゲームの ID を控え、ロック取得後に違っていれば無視する。終わったゲームへの質問が次のゲームで判定されるのを防ぐため。
- **メンション無効化**: ボットの投稿ではすべてのメンションを無効にする。質問文を引用して返すため、`@everyone` などで全員に通知が飛ぶのを防ぐ。
- **投稿失敗への対応**: スラッシュコマンドは最初に応答を保留してから処理する（ロック待ちで 3 秒の応答期限を超えないため）。チャンネルへの公開投稿に失敗したら、その本文を本人向けの返信に含める（giveup でお題が誰にも伝わらない事態を防ぐ）。質問への返信に失敗しても、判定や質問数はやり直さない。
- **長さの上限**: お題 1〜50 文字、補足 0〜300 文字、表示する質問文は 200 文字で省略する。これですべての投稿が Discord の上限 2,000 文字に収まる。

## Web 版

### ルールの違い

- ルームの URL か QR コードで集まる。ルーム番号を知っていれば誰でも入れる（友人どうしで遊ぶ前提で、それ以上の認証はしない）。お題は誰でも出せ、ギブアップも誰でもできる（出題者が抜けても終えられるように）。
- 出題者が誰かは、ゲーム中も終了後も表示しない。出題者もほかの参加者と同じく質問でき、言い当てれば正解になる。インサイダーゲームのように、お題を知る人が質問者に紛れて遊べるようにするため（誰だったかは参加者どうしで明かす）。Discord 版では出題者名を表示し、出題者の発言は質問として扱わない。
- 押して話すボタンか質問用の入力欄から送ったものは、すべて質問として扱う。末尾の「。．.、？?」を外してから「？」を付け直して `handle_question` に渡すので、「？」の規則は Discord 版と共通のまま、話す人は「？」を気にしなくてよい。「？」だけ・「。」だけの質問は送らない。
- ゲーム開始の通知だけは Web 用の文面にする。Discord 用の「最後に「？」をつけてね」は、声で「はてな」と言わせてしまうおそれがあるため。
- ブラウザがルームごとに合言葉を保存し、再読み込みや別のタブでも同じ参加者として戻る。ルームの中での名前は最初の入室時に固定する。履歴に残る発言者名と参加者一覧がずれないようにするため。

### 画面

- 夜を思わせる暗い配色にライム色の差し色を置き、ゴシックと明朝の対比で、秘密のお題を問いでほどくゲームの世界観を出す。装飾は CSS と SVG だけで作り、Web フォントや新しい実行時の依存は足さない。トップから接続切断の表示まで、すべての画面を同じデザインにそろえる。
- 回答履歴は、既知の回答形式だけをカードと割合バーで表示し、その他の通知・未知の形式は本文のまま表示する。サーバーは `GameService` の本文をそのまま送り、解析は画面側（`answer.js`）で行うので、回答の書式を変えるときは解析とそのテストも合わせて変える。
- ゲームが始まると、3 種類の開始の音声から 1 つを全員の画面で鳴らす。
- 名前・お題・質問は `textContent` で表示し、`innerHTML` は使わない。
- 補助の操作も 44px 以上の大きさにし、アニメーションは `prefers-reduced-motion` で止める。

### 設計上の判断

- **別プロセス**: `python -m insider_bot.web` で Discord ボットとは別に動かす。片方の再起動やエラーがもう片方に及ばないようにするため。中核（`GameService` など）は変更せず、ルームと参加者に振った整数 ID をチャンネル ID・ユーザー ID として渡す。
- **音声認識はブラウザ内蔵（Web Speech API）**: 無料で、押している間に途中結果を出せるため。Firefox など非対応のブラウザでは文字入力に切り替える。マイクの拒否や、iPhone の「設定」の「音声認識」で Safari がオフのとき（`service-not-allowed`）など使えないとわかるエラーは、`end` を待たずに文字入力に切り替える。iPhone の Safari はこの error の後に `end` を出さないため。`service-not-allowed` のときは、画像付きの設定のしかた（`static/iphone-voice.html`）へのリンクを入力欄の下に出し続ける（案内の文は数秒で消えるため）。`stop()` は全区間の確定を保証しないので、送る文字は「確定分＋未確定の末尾」にする。押している間に認識が勝手に終わったとき（Android で無音が続くなど）は、聞き取った分を残して聞き直す。聞き直すのはエラーなしか `no-speech` で終わったときだけで、`aborted` や分類していないエラーでは止めて、もう一度押すよう知らせる（聞き直してもすぐ同じく終わり、押している間ずっと開始と失敗を繰り返すため）。ボタンの外で離したかは、指を捕まえている間は `pointerleave` が使えないので座標で判定する。PC のスペースキーは、文字入力欄やほかのボタンにフォーカスがあるときと、ダイアログを開いているときは押して話すに使わない。
- **公開は Tailscale Funnel**: マイクには HTTPS が必要。Funnel なら無料・固定 URL・ドメイン不要で、受け付けのポートを開けずに済む。Cloudflare は独自ドメインなしだと固定 URL を得られない（Quick Tunnel は起動ごとに URL が変わる）。待ち受けは既定で `127.0.0.1` だけにし、外からは Funnel 経由でしか入れない。動かす場所と費用は [インフラ構成](infra.md)。
- **入室の失敗は終了コードで伝える**: ブラウザは WebSocket の接続に失敗したときの HTTP ステータスを読めないので、接続を受けてから独自の終了コード（`4404` ルームがない・`4409` 満員・`4400` 最初のメッセージが正しい `join` でない）で閉じる。画面はこれらのコードでは再接続しない。
- **送った質問の見張り**: 半開きの接続（スマホの回線切り替え直後など）では `WebSocket.send()` が失敗を知らせずに捨てる。質問を送ってから 5 秒間サーバーから何も届かなければ、届いていない可能性を知らせて文字を入力欄に戻し、接続を張り直す。送った後に接続が切れたときも同じく知らせる。
- **配信の順序**: 接続ごとに送信待ちの列を持ち、進行役（`RoomHub`）は列に積むだけで待たない。状態を変えてから積むまでの間に `await` を挟まない。asyncio は 1 スレッドなので「状態を変えた順＝画面に届く順」になり、再接続中の巻き戻りや「判定中」と結果の逆転が起きない。入室時は接続の登録と `snapshot` の積み込みを同じ流れで行うので、取りこぼしも重複もない。
- **判定は接続から切り離す**: 質問の判定を別タスクで動かし、結果を履歴に確定してから配る。判定中に質問者のタブが閉じても「判定中」のまま残らない。送信に失敗した接続と、送信待ちが 100 件たまった接続は、その接続だけを閉じる（画面は再接続して `snapshot` で追いつく）。
- **古い質問の排除（Web）**: 質問には画面が見ているゲームの ID を付け、今のゲームと違えば断る。ボタンを押している間に次のゲームが始まっても、前のゲームへの質問を新しいお題で判定しないため。事前の確認から `handle_question` が対象のゲームを控えるまでの間に `await` を挟まないので、確かめたゲームと判定するゲームが一致する。
- **お題と出題者は出題者の接続にだけ送る**: 入室時の `snapshot` と `room` の `you` に、出題者の接続にだけお題と補足を入れる。ゲームの見出し（`game`）には出題者名を入れないので、ほかの参加者は通信の中身を見ても出題者がわからない。
- **ルームの上限**: 同時に 50 個、1 ルーム 20 人。作成に認証や頻度制限がないので、上限のときは接続のないルームのうち最も古いものを消して空ける（空のルームを大量に作られても、遊んでいる人を締め出さない）。送信元ごとの制限は Funnel 経由の送信元の見分け方に頼ることになるので採らない。満員の判定は新しい参加者を作るときだけにし、合言葉の一致する参加者は戻れる。
- **ルームの片付け**: 10 分ごとに、誰も入らないまま 10 分たったルームと、誰も接続していない状態が 6 時間続いたルームを、進行中のゲームごと消す。消すのは接続のないルームだけなので、遊んでいる最中の画面からルームが消えることはない。`GameService` のチャンネルごとのロックはルームを消しても残るが、1 つ数百バイトなので消さない。
- **開始の音声はサーバーが選ぶ**: ランダムに選んだ音声を `sound` メッセージで全員に送り、全員が同じ声を聞く。同じ部屋や通話で遊ぶと、画面ごとに違う声が重なるため。状態ではなく一度きりの合図にして、再接続や途中参加の `snapshot` では鳴らさない。
- **音は Web Audio API で鳴らす**: ブラウザは操作のないページに音を出させないので、タップやキー操作のたびに `AudioContext` を動かしておく（iPhone は音声認識や着信のあとに止めるため）。合図が届いた時点で動いていなければ鳴らさない。待つと、次に画面を触ったときに遅れて鳴るため。そのため、ページを開いてから一度も触っていない人や、iPhone のマナーモードでは鳴らない。音声は AAC（`static/sounds/`、各 30KB 弱）で配り、最初に鳴らすときに読み込む。元の WAV は `assets/sounds/` に置く。
- **QR は画面側で作る**: ブラウザが開いている URL から作れば、サーバーが自分の公開 URL を知らなくて済む。サイト内の読み取りでは同じオリジンの `/r/<ルーム番号>` だけを受け付け、読み取った見知らぬ URL へは移動しない。
- **外部の CDN を使わない**: QR の生成（qrcode-generator 1.4.4）と読み取り（jsQR 1.4.0）は `static/vendor/` に版番号付きで同梱し、使うときだけ読み込む。外向き通信を抑えるため、版番号付きのファイルは 1 週間キャッシュさせ、それ以外は毎回更新を確かめる。同じ理由で、WebSocket で送る JSON は日本語を `\uXXXX` にエスケープしない（エスケープすると通信量が 3〜6 倍になる）。

## 将来の拡張

- ボイスチャンネルの聞き取り: ボットが VC に参加して発話を文字起こしし、ゲームを登録したテキストチャンネルの ID で `handle_question` を呼んで結果をそのチャンネルに投稿する。ボット自身の音声は呼ぶ前に除外する。
- 制限時間、インサイダーの役職・投票。
