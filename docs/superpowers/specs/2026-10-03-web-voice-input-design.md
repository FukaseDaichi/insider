# お題当てゲーム Web 版（押して話す音声入力）設計書

- 作成日: 2026-10-03
- ステータス: レビュー待ち

## 1. 目的

お題当てゲームを、Discord の外の Web サイトで、**ボタンを押している間に話した言葉を質問として送る**形で遊べるようにする。
判定とゲーム進行は既存の `GameService`・`JevJudge` をそのまま使い、Web は新しい入口として足す。

### 成功の条件

- 離れた場所にいる参加者が、各自の端末でルームの URL か QR コードから同じルームに入れる
- 回答者がボタンを押して話し、離すと質問が送られ、全員の画面に「判定中」→「はい／いいえと割合」が出る
- 押している間は認識中の文字が見え、ボタンの外で離すと取り消せる
- お題は出題者の画面にしか出ない
- Discord ボットは今までどおり動き続ける

### 対象外

- ログイン・アカウント
- ルームやゲームの保存（再起動で消える。Discord 版と同じ）
- サーバー側での文字起こし
- サイト内の通話（会話は Discord VC や Zoom などで行う）
- Discord のチャンネルと Web のルームの連携
- 1 人ごとの質問回数の制限

## 2. 決定事項と理由

| 項目 | 決定 | 理由・比べた案 |
|---|---|---|
| 遊ぶ場面 | 離れた場所から各自の端末で。会話は外部の通話で行う | サイトに通話は作らず、履歴を全員の画面に同期する |
| Discord ボット | 今のまま残し、Web は別のゲームとして並行 | Discord と Web のゲームはつながらない |
| 文字起こし | ブラウザ内蔵の音声認識（Web Speech API） | 無料・API キー不要・途中結果が出る。サーバーでの文字起こしは離すまで文字が出ず、ストリーミングは複雑で費用がかかる |
| 送信方法 | 離したら即送信。ボタンの外で離すと取り消し | 押している間に認識中の文字を見て判断できる |
| 公開方法 | Tailscale Funnel（`https://<マシン名>.<tailnet名>.ts.net`） | 完全無料・固定 URL・ドメイン不要・ポートを開けない。Cloudflare は独自ドメインなしだと固定 URL を得られない（Quick Tunnel は起動ごとに URL が変わる試験用） |
| QR コード | 招待パネルでの大きな表示と、サイト内の読み取り画面の両方 | 画面共有や、PC の画面を自分のスマホで読む場面に使う |

## 3. 技術選定

| 項目 | 選定 |
|---|---|
| Web サーバー | aiohttp（HTTP と WebSocket の両方。ASGI サーバー不要） |
| 画面 | ビルド不要の HTML・CSS・素の JavaScript（ES モジュール） |
| 音声認識 | Web Speech API（`SpeechRecognition` / `webkitSpeechRecognition`、`lang="ja-JP"`） |
| QR 生成 | qrcode-generator（MIT）。リポジトリに同梱 |
| QR 読み取り | jsQR（Apache-2.0）。リポジトリに同梱し、読み取り画面を開いたときだけ読み込む |
| テスト | pytest・pytest-asyncio（既存）、aiohttp の `test_utils`、`node --test`（JS の純粋関数のみ） |

外部の CDN は使わない。ライブラリは版番号付きのファイル名で `static/vendor/` に置き、ライセンス文も同梱する。

## 4. 画面と流れ

画面は 1 枚の `index.html` で、URL のパスによってトップページかルーム画面を出す。

### 4.1 トップページ（`/`）

- 名前の入力欄（1〜20 文字。ブラウザに記憶し、次回は入った状態で出す）
- 「ルームを作る」: ルームを作ってそのルームへ移動し、招待パネルを開く
- 「📷 QR で参加」: 読み取り画面を開く（§4.5）

### 4.2 ルーム画面（`/r/<ルーム番号>`）

ルーム番号は 6 文字。紛らわしい文字（0・O・1・I・L）を除いた英大文字と数字から作る（例: `K7Q2MX`）。

```
 回答者の画面                          出題者の画面
┌─────────────────────────┐    ┌─────────────────────────┐
│ ルーム K7Q2MX       [招待] │    │ ルーム K7Q2MX       [招待] │
│ 出題者 たろう・質問 5・3:21    │    │ 出題者 あなた・質問 5・3:21    │
│ 参加者: たろう はなこ じろう   │    │ 🤫 お題「りんご」補足:赤い果物 │
├─────────────────────────┤    ├─────────────────────────┤
│ 🎮 ゲーム開始！…            │    │ 🎮 ゲーム開始！…            │
│ はなこ ❓ 果物ですか？        │    │ はなこ ❓ 果物ですか？        │
│ ✅ はい  はい 82% ██████░ │    │ ✅ はい  はい 82% ██████░ │
│ じろう ❓ 赤いですか？        │    │ じろう ❓ 赤いですか？        │
│        … 判定中            │    │        … 判定中            │
├─────────────────────────┤    ├─────────────────────────┤
│  「丸い形ですか」← 認識中     │    │ あなたは出題者です          │
│     ╭─────────────╮      │    │                         │
│     │ 🎙 押して話す  │      │    │  [ギブアップ（お題を公開）]  │
│     ╰─────────────╯      │    │                         │
│ 離すと送信／外で離すと取消      │    │                         │
│  ⌨ 文字で質問   ギブアップ   │    │                         │
└─────────────────────────┘    └─────────────────────────┘
```

- 名前が記憶されていなければ、入室前に名前を聞く
- 上部に、出題者・質問数・経過時間を常に出す（Discord の `/odai status` に当たる操作は作らない）。経過時間は画面側で 1 秒ごとに進める
- 参加者の一覧は、接続中かどうかを見分けられるようにする
- 履歴は `GameService` が返す本文（Discord と同じ文面）をそのまま出す。改行はそのまま表示する
- ゲームがないときは操作欄に「お題を出す」を出す。押すとお題（1〜50 文字）と補足（任意・300 文字まで）の入力欄が開く
- 出題者の画面では押して話すボタンを出さず、お題と補足を上部に出す
- **ギブアップは誰でもできる**（Discord 版と同じ）。出題者には大きなボタンで、回答者には小さなリンクで出し、確認を挟む。出題者が抜けたままでもゲームを終えられるようにするため
- 接続が切れている間は、送信の操作をすべて無効にする

### 4.3 遊ぶ流れ

1. 誰かがルームを作り、招待パネルの URL か QR を通話のチャットなどで共有する
2. 参加者が URL を開くか QR を読んで、名前を入れて入室する
3. 誰かが「お題を出す」でゲームを始める。全員の履歴に「🎮 ゲーム開始！」が出る
4. 回答者は押して話すボタンで質問する。全員の履歴に「判定中」の行が出て、判定が済むと結果に置き換わる
5. 正解かギブアップで終了する。また誰でも「お題を出す」から次のゲームを始められる

途中から入った人や、再読み込みした人にも、それまでの履歴を出す。

### 4.4 招待パネル

- ルーム画面の「招待」で開く。ルームを作った直後は自動で開く
- `location.origin + "/r/" + ルーム番号` の QR を画面幅いっぱい（最大 320px 程度）で出す。誤り訂正レベルは M
- ルーム番号、「URL をコピー」「閉じる」を並べる
- QR はブラウザが今開いている URL から作る。サーバーが自分の公開 URL（…ts.net）を知る必要がないようにするため

### 4.5 QR の読み取り画面

- 背面カメラを優先して起動する（`facingMode: "environment"`、iOS 向けに `playsinline`）
- 映像を 1 秒に 10 回程度キャンバスに写して jsQR で読む
- **このサイトのルーム URL だけを受け付ける**: 同じオリジンで、パスが `/r/<6 文字のルーム番号>`（末尾の `/` は可、クエリやハッシュは無視）のとき、そのルームへ移動する。それ以外は「このゲームの QR コードではありません」と出して読み取りを続ける。読み取った見知らぬ URL へ移動しないため
- 閉じるか移動するときはカメラを止める
- カメラが許可されない・使えないときは「スマホ標準のカメラでも読み取れます」と案内する

## 5. 押して話すボタン

### 5.1 操作

| 操作 | 動き |
|---|---|
| 押す | 認識を始める。始まるまでは「準備中…」、始まったら（`start` イベント）ボタンを赤くして「聞いています…」。**赤くなってから話す** |
| 押している間 | ボタンの上に認識中の文字（確定分＋途中結果）を出す |
| ボタンの外に指が出る | 「離すと取り消し」と表示を変える |
| ボタンの上で離す | 認識を止め、最終結果を待って送る |
| ボタンの外で離す・タッチが中断された | 認識を中止し「取り消しました」 |
| 認識が始まる前に離した | 中止して「長押ししてから話してください」 |
| 20 秒押し続けた | そこで止めて、そこまでの内容を送る |
| PC: スペースキー長押し | 押す・離すと同じ。押している間に Esc で取り消し。文字入力欄にフォーカスがあるときは反応しない |

### 5.2 細かい決まり

- 認識の設定: `continuous = true`、`interimResults = true`、`lang = "ja-JP"`
- 送る文字は、確定した結果をつないだもの。確定分がなく途中結果だけが残っていれば、途中結果を使う
- 押している間に認識が勝手に終わったとき（Android などで無音が続くと起きる）は、確定分を保持したまま認識を再開する
- 何も聞き取れなかったら「聞き取れませんでした」と出して送らない
- 送ろうとしたときに接続が切れていたら「接続が切れているため送れませんでした」と出し、文字を文字入力欄に移して送り直せるようにする
- ボタンには `touch-action: none`、文字選択の禁止、長押しメニューの抑止（`-webkit-touch-callout: none`、`contextmenu` の取り消し）を指定する。押したままの間は `setPointerCapture` で指の位置を追う
- 初回はブラウザがマイクの許可を求める。許可の操作中に指を離すと「認識が始まる前に離した」扱いになるので、「許可したら、もう一度押して話してください」と案内する

### 5.3 エラー

| 認識のエラー | 表示 | その後 |
|---|---|---|
| `not-allowed` / `service-not-allowed` | マイクが許可されていません。ブラウザの設定から許可するか、文字で質問してください | 文字入力に切り替える |
| `audio-capture` | マイクが見つかりません | 文字入力に切り替える |
| `no-speech` | 聞き取れませんでした | 何も送らない |
| `network` | 音声認識サーバーに接続できませんでした | 何も送らない |
| `aborted`（自分で中止したとき） | なし | なし |

### 5.4 非対応ブラウザと文字入力

- `SpeechRecognition` も `webkitSpeechRecognition` もないブラウザ（Firefox など）では、ボタンの代わりに文字入力欄を出し、「音声入力は Chrome / Edge / Safari で使えます」と案内する。iPhone では Siri（音声入力）を有効にしておく必要がある旨も添える
- 対応ブラウザでも「⌨ 文字で質問」で文字入力に切り替えられる。Enter か送信ボタンで送る

## 6. 構成

```
src/insider_bot/
├── config.py            # Web 用の読み込み load_web_config を追加（しきい値・タイムアウトの検査は共通化）
└── web/
    ├── __init__.py
    ├── __main__.py      # 起動: python -m insider_bot.web
    ├── rooms.py         # ルームと参加者の管理（ネットワークに依存しない）
    ├── hub.py           # 操作を GameService に渡し、結果を接続に配る（WebSocket に依存しない）
    ├── server.py        # aiohttp のアプリ: ルーティング、WebSocket の受信ループ
    └── static/
        ├── index.html
        ├── style.css
        ├── app.js       # 画面全体（トップ・ルーム・接続・再接続）
        ├── speech.js    # 押して話す（Web Speech API の扱い）
        ├── qr.js        # 招待パネルと読み取り画面
        ├── roomurl.js   # 読み取った文字列がルーム URL かを判定する純粋関数
        └── vendor/      # qrcode-generator・jsQR（版番号付き）とライセンス文
tests/
├── test_web_config.py
├── test_web_rooms.py
├── test_web_hub.py
├── test_web_server.py
└── js/roomurl.test.mjs
deploy/
└── insider-web.service
```

### 6.1 各部品の役割

- **rooms.py**: `Room`（番号、整数の ID、参加者、履歴、最終活動時刻）と `Player`（整数の ID、名前、合言葉、接続中かどうか）を持つ `RoomRegistry`。作成・入室・合言葉での復帰・上限・片付けを担う。時計は差し替えられるようにする
- **hub.py**: `RoomHub`。接続から届いた操作を検査し、`GameService` を呼び、結果を本人か全員に配る。送り先は `send(message)` を持つ接続の抽象で、テストでは偽物を使う。ヘッダーに出す質問数・経過時間は `GameManager.get()` から読むだけで、書き換えない
- **server.py**: HTTP の配信と、WebSocket のメッセージを JSON として `RoomHub` に渡す受信ループ。判断は持たない
- **既存部分**: `GameService`・`GameManager`・`JevJudge`・`format` は変更しない。ルームの整数 ID をチャンネル ID として、参加者の整数 ID をユーザー ID として渡す。名前は Markdown のエスケープをせずに渡す（エスケープは Discord 側だけで行っている）

### 6.2 起動と設定

- `uv run --env-file .env python -m insider_bot.web` で起動する。Discord ボットとは別のプロセスにし、ゲームも再起動も独立させる
- 必須の環境変数は `TYPESAFE_API_KEY` だけ。`DISCORD_TOKEN` は要らない

| 環境変数 | 必須 | 既定 | 説明 |
|---|---|---|---|
| `TYPESAFE_API_KEY` | ✓ | — | TypeSafe API キー |
| `CORRECT_THRESHOLD` | | 0.8 | Discord 版と共通 |
| `JEV_TIMEOUT_SECONDS` | | 10 | Discord 版と共通 |
| `WEB_HOST` | | 127.0.0.1 | 待ち受けるアドレス |
| `WEB_PORT` | | 8080 | 待ち受けるポート |

- 終了時に Jev のクライアントを閉じる（aiohttp の `on_cleanup`）

## 7. やり取り

### 7.1 HTTP

| メソッドとパス | 内容 |
|---|---|
| `GET /`、`GET /r/{番号}` | `index.html`。ルームの有無は WebSocket の接続時に分かる |
| `GET /static/...` | 画面のファイル。アプリのファイルは `Cache-Control: no-cache`（更新日時で 304 を返す）、`vendor/` は版番号付きなので 1 週間キャッシュ |
| `POST /api/rooms` | ルームを作って `201 {"code": "K7Q2MX"}`。上限に達していたら `503` と理由の文 |
| `GET /r/{番号}/ws` | WebSocket |

### 7.2 WebSocket

- 1 つのブラウザのタブにつき 1 本。受け取るメッセージは最大 4KB。30 秒ごとに死活確認（aiohttp の `heartbeat`）
- 存在しないルームや満員のルームは、接続を受けてから独自の終了コードで閉じる（ブラウザは接続に失敗したときの HTTP ステータスを読めないため）
  - `4404`: ルームが見つからない
  - `4409`: ルームが満員
  - `4400`: 最初のメッセージが `join` でない、または形式が不正
- メッセージはすべて JSON で、`type` で種類を表す

**画面 → サーバー**

| type | 中身 | 内容 |
|---|---|---|
| `join` | `name`、`token`（初回は `null`） | 最初に必ず送る。合言葉が一致すれば同じ参加者として戻り、名前を更新する |
| `start` | `topic`、`hint` | お題を出す |
| `ask` | `text` | 質問する |
| `giveup` | なし | ギブアップ |

**サーバー → 画面**

| type | 中身 | 送り先 | 内容 |
|---|---|---|---|
| `welcome` | `token` | 本人 | 合言葉。画面はルームごとにブラウザへ保存する |
| `snapshot` | `room`、`log` | 本人 | 入室・再接続のたびに、その時点の全体を送る |
| `room` | `players`、`game`、`you` | 全員（`you` は接続ごと） | 参加者・ゲームの状況が変わるたびに送る |
| `entry` | 履歴の 1 行 | 全員 | 行の追加。同じ `id` なら置き換え |
| `notice` | `text` | 本人 | 本人だけへの通知（`GameService` の private や入力エラー） |

- `players`: `[{"name": "はなこ", "online": true}, ...]`
- `game`: ゲームがなければ `null`。あれば `{"setter": "たろう", "questions": 5, "elapsed": 201.3}`（`elapsed` は送った時点の経過秒数）
- `you`: `{"is_setter": true, "topic": "りんご", "hint": "赤い果物"}`。**お題と補足は出題者の接続にだけ入れる**。回答者には `{"is_setter": false}` だけを送る
- 履歴の 1 行: `{"id": 12, "author": "はなこ" | null, "text": "…", "pending": false}`。履歴は最新 300 行まで持つ

### 7.3 操作ごとの処理

**質問（`ask`）**

1. 文字の前後の空白を除き、末尾の「。．.、」を除く。空なら `notice` で断る。200 文字を超えたら断る
2. 末尾が「？」か「?」でなければ「？」を付ける。押して話すボタン（または質問用の文字入力欄）を使うこと自体が質問の合図なので、話す人が「？」を気にしなくて済むようにするため。`GameService` の「？」の規則はそのまま
3. ゲームがない、または本人が出題者なら、`notice` で断る（「進行中のゲームはありません」「出題者は質問できません」）
4. `❓ <質問>\n… 判定中` の行（`pending: true`）を全員に配る
5. `GameService.handle_question(ルームID, 参加者ID, 名前, 質問)` を呼ぶ
6. 結果の public で同じ行を置き換える（`pending: false`）。判定失敗のときは既存の「⚠️ 判定できませんでした。もう一度どうぞ」になる
7. 結果が空（判定を待つ間にゲームが終わったなど）なら、行を `❓ <質問>\n— ゲームが終わったため取り消しました` に置き換える
8. `room` を全員に配る（質問数・ゲーム終了の反映）

質問は `GameService` がルームごとに 1 つずつ判定するので、同時に届いても届いた順に処理される。

**お題を出す（`start`）**: 長さを検査し、`GameService.start` を呼ぶ。private は `notice` で本人へ、public は新しい行として全員へ配り、`room` を全員に配る。

**ギブアップ（`giveup`）**: `GameService.giveup` を呼び、public を新しい行として全員へ、private を `notice` で本人へ配り、`room` を全員に配る。

## 8. ルームと参加者の管理

- ルームと参加者の整数 ID は、プロセスの中で 1 から振る
- 合言葉は `secrets.token_urlsafe(16)`。画面は `localStorage` にルームごとに保存し、`join` で送る。名前は全ルーム共通で保存する
- 1 人が複数のタブで接続してもよい。本人あての送信はその参加者のすべての接続に送る。接続が 1 本でもあれば「接続中」
- 上限: ルームは同時に 50 個、1 ルームの参加者（一度でも入った人）は 20 人まで
- 片付け（10 分ごとと、ルーム作成時に行う）
  - 誰も入らないまま 10 分たったルームを消す
  - 誰も接続していない状態が 6 時間続いたルームを消す
  - 消すときは、そのルームの進行中ゲームも `GameManager.end()` で終える
- 既知の制限: `GameService` はチャンネルごとのロックを削除しないため、ルームを作るたびにロックが 1 つずつ残る。1 つ数百バイトで、問題になる量ではないので今回は直さない

## 9. エラー時の動き

| 起きること | 画面の動き |
|---|---|
| 通信が切れた | 上部に「再接続中…」を出し、1→2→4→8→10 秒（以後 10 秒）の間隔で再接続する。つながったら `join` をやり直し、`snapshot` で画面を作り直す |
| ルームが見つからない（`4404`） | 「ルームが見つかりません（サーバーが再起動した可能性があります）」とトップページへのリンク。再接続はしない |
| ルームが満員（`4409`） | 「このルームは満員です」。再接続はしない |
| ルームを作れない（`503`） | 「今はルームを作れません。しばらくしてからどうぞ」 |
| Jev の判定に失敗した | 判定中の行が「⚠️ 判定できませんでした。もう一度どうぞ」になる |
| 判定を待つ間に誰かが正解した | 判定中の行が「— ゲームが終わったため取り消しました」になる |
| マイク・音声認識のエラー | §5.3 |
| カメラが使えない | §4.5 |

## 10. 入力の制限と安全対策

- 長さの上限（画面とサーバーの両方で検査する）: 名前 1〜20 文字、お題 1〜50 文字、補足 300 文字まで、質問 200 文字まで
- 名前・質問・お題などは、画面ではすべて `textContent` で出す。`innerHTML` は使わない
- 公開 URL なので、ルームと参加者の上限（§8）でメモリの使いすぎを防ぐ
- 待ち受けは既定で `127.0.0.1` のみ。外からは Tailscale Funnel 経由でしか入れない
- QR の読み取りで受け付けるのは、このサイトのルーム URL だけ（§4.5）
- ルーム番号を知っていれば誰でも入れる。友人どうしで遊ぶ前提で、それ以上の認証はしない

## 11. デプロイ（e2-micro）

- `deploy/insider-web.service`: `insider-bot.service` と同じ作り（起動前に `uv sync --frozen --no-dev`、落ちたら再起動）で、`python -m insider_bot.web` を動かす
- `deploy/setup.sh`: 両方のユニットを配置・有効化・再起動するように広げる。`.env` の検査は今のまま（両方を動かすので `DISCORD_TOKEN` と `TYPESAFE_API_KEY` が必要）
- Tailscale は、ログインにブラウザでの認証が要るので、`deploy/README.md` に手順を書いて手作業で行う
  1. `curl -fsSL https://tailscale.com/install.sh | sh`
  2. `sudo tailscale up`（表示された URL を開いてログインする）
  3. `sudo tailscale funnel --bg 8080`（初回は管理画面で Funnel を有効にするリンクが出る。設定は再起動後も残る）
  4. 表示された `https://….ts.net` をスマホで開き、ルームを作って質問できることを確かめる（Funnel が WebSocket を通すことの確認を兼ねる）
- GCP のファイアウォールは今のまま閉じておく
- 無料枠の外向き通信（月 1GB）: 画面一式は数百 KB 以下で、jsQR は読み取り画面を開いたときだけ読み込む。キャッシュも効かせるので、友人どうしで遊ぶ量なら収まる
- 手元での開発: `uv run --env-file .env python -m insider_bot.web` で起動し、`http://localhost:8080` を開く（localhost は HTTPS なしでもマイクとカメラが使える）。スマホでの確認は、Mac で一時的に `tailscale funnel 8080` を使う
